EPC BETHEL — INSTALLATION RAPIDE (VERSION 1.19.2)

IMPORTANT
Cette archive contient le code source consolidé des étapes 1 à 7 (revue de pré-livraison). La compilation complète et les migrations n'ont pas encore été validées sur un projet Supabase réel. Commence toujours par un projet de développement et une sauvegarde.

1. Décompresser EPC_BETHEL_ETAPE_7_VALIDATION_FINALE.zip.
2. Installer Node.js 20.9 ou supérieur.
3. Ouvrir un terminal à la racine du dossier EPC_BETHEL_APP.
4. Installer les dépendances : npm install
   Cette commande génère aussi `package-lock.json` ; conserve ce fichier dans le dépôt pour figer les dépendances.
5. Copier .env.example vers .env.local.
6. Renseigner les variables nécessaires :
   - NEXT_PUBLIC_SUPABASE_URL
   - NEXT_PUBLIC_SUPABASE_ANON_KEY
   - NEXT_PUBLIC_SITE_URL
   - EPC_BETHEL_REGISTRATION_CODE (secret aléatoire long pour les inscriptions)
   - SUPABASE_SERVICE_ROLE_KEY uniquement si les opérations serveur d'invitation en ont besoin.
   IMPORTANT : SUPABASE_SERVICE_ROLE_KEY est strictement secrète. Ne jamais la préfixer par NEXT_PUBLIC_, la placer dans le navigateur, ni la committer dans Git.

7. Dans un projet Supabase DE DÉVELOPPEMENT, sauvegarder d'abord la base, puis examiner et appliquer les migrations dans l'ordre ci-dessous. Arrêter au premier échec :
   001_initial_schema.sql
   002_financial_workflows.sql
   003_concessions_achats_patrimoine_auth.sql
   004_scolarite_echeances_transactionnelles.sql
   005_scolarite_concessions.sql
   006_paiements_recus.sql
   007_tresorerie_comptabilite.sql
   008_achats_patrimoine_workflows.sql
   009_securite_parametres_imports.sql
   010_add_observateur_role.sql
   011_auth_admin_and_observer_access.sql
   012_school_management_completion.sql
   013_financial_integrity_reporting.sql
   014_management_reports_asset_integration.sql
   015_admin_registration_code_settings.sql
   016_notes_bulletins.sql
   017_bank_reconciliation_workflow.sql
   018_notes_bulletins_workflows.sql
   019_finance_scolaire_reductions_echeanciers.sql
   020_fix_school_fee_ledger_ambiguity.sql
   021_treasury_account_types_and_creation.sql

8. Dans Supabase Auth, configurer le fournisseur e-mail, les paramètres de connexion par mot de passe, les URL autorisées et les redirections de l'application. Tester la création de compte avec code d'accès, puis la connexion par adresse e-mail et mot de passe depuis /login et /register. Le fonctionnement réel dépend de la configuration e-mail et des URL du projet Supabase.

9. Administrateur principal prévu : minnhindje@gmail.com. Vérifier la propriété de l'adresse et son profil dans Supabase après l'application des migrations. Ne jamais attribuer le rôle admin à partir d'un champ modifiable par l'utilisateur public. Le code EPC_BETHEL_REGISTRATION_CODE sert à autoriser les inscriptions ; il n'est pas demandé lors des connexions suivantes.

10. Lancer les contrôles dans cet ordre après installation réussie des dépendances :
    npm run test:release
    npm run preflight
    npm run typecheck
    npm run build
    npm run dev
    Puis ouvrir http://localhost:3000.

FONCTIONNALITÉS CONCERNÉES PAR L’ÉTAPE 4 ET L’ÉTAPE 5
- Registre des frais scolaires avec pagination serveur et affichage du matricule, de la classe et de l'année scolaire.
- Liste des inscriptions qui possèdent un reste à payer pour encaisser les règlements.
- Affectation transactionnelle des paiements aux échéances les plus anciennes puis aux frais ponctuels.
- Calculs financiers et indicateurs du tableau de bord agrégés dans PostgreSQL plutôt que calculés à partir d'un échantillon de lignes récentes.
- Validation des dépenses avec contrôle du solde et journalisation ; transferts entre comptes sous forme de deux mouvements liés.
- Refus SQL des paiements, validations de dépenses et transferts datés dans le futur.
- Date d'effet prise en compte pour les soldes d'ouverture des comptes.

FONCTIONNALITÉS CONCERNÉES PAR L’ÉTAPE 5
- Rapports réels depuis PostgreSQL : synthèse financière, impayés, encaissements, dépenses, journal de caisse/banque, achats, réceptions, inventaire et maintenance.
- Filtres dates/recherche, filtre année scolaire pour rapports d’impayés et encaissements, pagination, export Excel limité à 50 000 lignes et impression.
- Réceptions de commandes affichées depuis l’historique réel ; la réception d’immobilisations génère une fiche par unité entière en inventaire. La réception ne génère pas de sortie de trésorerie : le règlement doit être enregistré séparément via Dépenses.
- Modification des biens et maintenance enregistrée par RPC avec mise à jour du statut.
- Migration `014_management_reports_asset_integration.sql` à exécuter après la migration 013.

SCÉNARIOS À TESTER AVANT TOUTE UTILISATION RÉELLE
- Connexion OTP, invitation, inscription par code et tests des profils administrateur, modification et observateur.
- Frais annuels, réductions, échéanciers de 1 à 6 versements, paiement partiel, paiement complet et refus d'un trop-perçu.
- Dépense en brouillon, validation avec solde suffisant/insuffisant, annulation et contrepassation.
- Transfert caisse → banque : les deux mouvements doivent être liés et le total de trésorerie ne doit pas changer.
- Compte dont la date d'ouverture est future et refus des opérations futures.
- Comparaison des totaux affichés avec des requêtes de contrôle dans PostgreSQL.
- Tests des politiques RLS et des droits d'exécution RPC pour chaque profil.

ÉTAPE 7 — REVUE FINALE DE LIVRAISON
- `npm run preflight` contrôle les références internes, la continuité des migrations, les RPC/tables utilisées et certains points de sécurité statique. Il ne remplace pas la compilation ou les tests Supabase.
- Voir `RAPPORT_ETAPE_7_VALIDATION_FINALE.md` et `CHECKLIST_MISE_EN_SERVICE.md` pour les résultats et les validations requises.

LIMITES CONNUES
- Certains écrans opérationnels conservent des limites d’affichage ; pour un rapport complet, utiliser le module Rapports paginé côté serveur.
- Le module de rapports détaillés et les parcours achats/patrimoine demandent encore des tests réels sur la base Supabase de développement.
- Aucun build complet ni test end-to-end de production n'est certifié dans cette archive. Les vérifications syntaxiques et statiques ne remplacent pas les tests dans un environnement configuré.
- Ne jamais ajouter de secrets réels à l'archive. Ne déployer en production qu'après réussite des tests, vérification RLS, sauvegarde et revue des migrations.

MISE À JOUR — MODULES SCOLAIRES ET RAPPROCHEMENT BANCAIRE
Après validation sur une base de test, exécuter dans Supabase SQL Editor, dans l’ordre :
1. supabase/migrations/016_notes_bulletins.sql
2. supabase/migrations/017_bank_reconciliation_workflow.sql
Le module Notes et bulletins permet de saisir des notes sur 20, avec coefficient, et d’exporter un relevé CSV. Il faut créer les matières dans school_subjects avant la saisie.
Le module Banque permet d’importer un relevé CSV avec les colonnes date, libelle, debit, credit (reference facultative), puis de rapprocher les lignes avec les mouvements validés du compte bancaire correspondant.
Ne lancez pas les migrations directement en production sans sauvegarde et validation préalable.

ÉTAPE SUPPLÉMENTAIRE DE BASE DE DONNÉES
1. Sauvegardez la base Supabase.
2. Vérifiez que les migrations 001 à 021 sont appliquées avant de lancer la migration 022.
3. En préproduction, exécutez une seule fois le fichier supabase/migrations/022_cash_register_single_ledger_and_controls.sql.
4. Testez un paiement espèces, un paiement Orange Money/Wave/Moov, une dépense par canal, un comptage physique, une ligne manuelle et ses contrôles de modification/suppression.
5. Ne déployez pas en production avant d’avoir validé les soldes, les autorisations RLS et le build Next.js.
